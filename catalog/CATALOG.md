# Catalog Parity Checklist

This document tracks the **bindings-based catalog** (`nutrient_flutter/catalog/`)
against the **legacy example app** (`nutrient_flutter/example/`). The goal is
to reach feature parity with the legacy example using only the new
`NutrientPlatformAdapter` / `NutrientController` / `NutrientDocumentInterface`
surface.

**Workflow:** one example per PR. We pick a single 🔲 row, land it end-to-end
(page + manual verification on Android + iOS + Maestro flow), update this
table in the same PR, then move to the next one. Don't bulk-port multiple
examples in one PR.

For each example, the loop is:

1. Implement the page against the bindings API.
2. Verify it works on Android + iOS (and Web where applicable).
3. Add a Maestro flow that drives it.
4. Tick the row below.

If something is partially working or blocked on a missing API, note the gap in
the **Gaps to close** column so we know what to land next.

**Out of scope:** the legacy example's "Global / `Nutrient.present(...)`"
entries are method-channel-only and have no equivalent on the bindings
surface. They are not tracked here.

## Status legend

| Symbol | Meaning |
| --- | --- |
| ✅ | Implemented in catalog, manually verified on Android and iOS, Maestro flow exists |
| 🟡 | Implemented in catalog, manually verified, **no Maestro flow yet** |
| 🟠 | Partially implemented — works on some platforms or some operations only |
| 🔲 | Not yet ported |
| 🚫 | Skipped — see **Gaps to close** for the blocking API gap |

Bookkeeping: keep the table sorted as **ported first** (✅/🟡/🟠), **planned**
next (🔲), **blocked** last (🚫). When a row moves between sections, move
the whole row — don't leave duplicate entries.

## Maestro flow conventions

- Place flows under [`ui-tests/catalog/flows/`](../../ui-tests/catalog/flows/),
  named `<platform>-<example>.yaml` (e.g.
  `android-platform-adapter.yaml`,
  `ios-platform-adapter.yaml`,
  `web-platform-adapter.yaml`). The platform-level
  aggregators ([`android-flow.yaml`](../../ui-tests/catalog/android-flow.yaml) /
  [`ios-flow.yaml`](../../ui-tests/catalog/ios-flow.yaml) /
  [`web-flow.yaml`](../../ui-tests/catalog/web-flow.yaml)) run every flow for
  that platform via `runFlow:`.
- Each example page surfaces a stable semantic marker once its golden-path
  state is reached (see `basicExampleReadyLabel`, `headlessExampleReadyLabel`
  in the existing files). New flows should assert on those labels **when
  there is no embedded native PlatformView on screen** — once a Nutrient
  fragment / view controller takes over, Maestro reads the *native viewer's*
  accessibility tree (e.g. `scientific-paper` title overlay, `1 / N` page
  chip) instead of Flutter's. Assert against those native labels for any
  page that hosts a `NutrientDocumentView`.
- Flows run on the Android emulator and iOS simulator listed in
  `~/.claude/projects/.../memory/run_build_commands.md`. Web flows require
  the catalog to be served via `flutter run -d chrome --web-port=8080`.

## Workflow (one PR per row)

1. Pick the next 🔲 row.
2. Implement the page, wire it into [pages/home_page.dart](lib/pages/home_page.dart).
3. Run on Android + iOS; if a platform fails, drop the row to 🟠 and capture
   the gap in **Gaps to close**.
4. Add the Maestro flow; if it passes on both platforms, flip the row to ✅.
5. Update this table in the same PR.

A row never moves to ✅ without (a) manual verification on both Android and
iOS and (b) a passing Maestro flow.
